## 1. Feasibility Analysis

- Problem / trigger:
  - Product decision (2026-10-04): effort is stored and shown as **RIR (reps in reserve)**, not RPE. The hypertrophy dose–response concept (Performance Progression = exercise + load + reps + RIR) and the coaches' own language are RIR-based.
  - Training History will display effort on every row. Shipping History on RPE and converting afterwards would mean redoing its UI and contract, so this change goes first.
- Options considered:
  1. Keep `rpe` storage; convert to RIR only in the UI (`RIR = 10 − RPE`).
  2. Store both `rpe` and `rir` columns, one derived.
  3. Rename every RPE column and API field to RIR and convert stored values once (`rir = 10 − rpe`).
- Trade-offs (per option):
  - Option 1 needs no migration, but the stored value, the API, and the UI then disagree. Every future reader (History, decision engine, AI layer) has to remember the conversion, and AI output would be validated against the wrong scale.
  - Option 2 duplicates one fact in two columns that can drift. There is no consumer that needs RPE.
  - Option 3 is a one-time, cross-cutting rename (5 columns, API fields, about 25 web files), but afterwards storage, contract, and UI all speak one scale.
- Selected option and why:
  - Option 3. One measure, one name, end to end. The rename is mechanical and fully covered by existing integration and unit tests once they are renamed too.
- Risks & unknowns:
  - **Breaking API rename.** `rpe` → `rir` in request and response bodies. Web (Vercel) and API (Cloud Run) must deploy as one release; see Backward compatibility.
  - **Value conversion is lossy only at the edges.** RPE 1–10 maps to RIR 9–0. RIR is constrained to 0–9 so the down migration (`rpe = 10 − rir`) stays inside the old 1–10 check.
  - Decimal values (for example RPE 8.5 → RIR 1.5) remain allowed, as today (`numeric`).
  - Existing staging/production rows with RPE are converted in place. Whether pilot athletes logged RPE meaning "RIR" by mistake cannot be detected; they are converted mechanically.
  - Voice Command (§3.9) is contract-only (not implemented). Its `CREATE_SET_LOG` example field is renamed in the contract only.
- Dependencies / blockers:
  - None in code. Requires an ordered staging deploy (migration → API → web).

## 2. Technical Design

- Affected files/components:
  - Migration: `apps/api/migrations/0011_rpe_to_rir.up.sql`, `.down.sql`, `verify_0011_rpe_to_rir.sql`
  - Backend: `apps/api/internal/prescription/`, `internal/workout/`, `internal/scheduledworkout/`, `internal/workoutsession/`, `cmd/api/main.go` (+ their tests)
  - Docs: API contract, schema relationships, frontend UI spec, MVP spec (examples such as `4 × 5 @ RPE 8` → `4 × 5 @ 2 RIR`)
  - Web: Calendar builder (`app/coach/calendar/*`), template builder (`app/coach/workouts/page.tsx`), session (`app/session/[id]/*`), `lib/prescription-summary.ts`, i18n `en`/`zh-TW` messages (+ tests)
- Schema changes (`0011_rpe_to_rir`), one transaction:

  | Table | From | To |
  | --- | --- | --- |
  | `workout_exercises` | `target_rpe` | `target_rir` |
  | `workout_exercise_set_overrides` | `rpe_override` | `rir_override` |
  | `scheduled_workout_exercises` | `target_rpe` | `target_rir` |
  | `scheduled_workout_planned_sets` | `target_rpe` | `target_rir` |
  | `set_logs` | `rpe` | `rir` |

  For each column: drop the old `*_rpe_check`, `RENAME COLUMN`, `UPDATE … SET x = 10 − x WHERE x IS NOT NULL`, add `*_rir_check` `CHECK (x IS NULL OR x BETWEEN 0 AND 9)`. The overrides table's "at least one override present" check follows the rename automatically. Down migration reverses it (`rpe = 10 − rir`, restore 1–10 checks). `verify_0011` asserts that no RPE-named columns or constraints remain and that values are within 0–9.
- API changes (contract updated **before** code, per AGENTS.md §6):
  - Field rename only, no route/status/authorization change: `plan.defaults.rpe` → `rir`, `overrides[].rpe` → `rir`, `plan.sets[].rpe` → `rir`, `setLogs[].rpe` → `rir`, `POST /sessions/{id}/set-logs` and `PATCH /set-logs/{id}` body `rpe` → `rir`.
  - Validation message: `rir must be between 0 and 9`.
  - The workout/scheduling/set-log handlers do not use `DisallowUnknownFields`, so a stale client's `rpe` key would be silently dropped. Each affected request decoder therefore explicitly rejects a legacy `rpe` key with `400 INVALID_ARGUMENT` (`rpe is no longer accepted; use rir`). This guard is temporary and is removed in a follow-up once no client sends `rpe`.
- Frontend state/UI impact:
  - Labels: `RIR` (zh-TW keeps the Latin abbreviation, as RPE did). Inputs accept 0–9, step 0.5. Summary format `4 × 5 @ 2 RIR`.
  - Calendar "Use default RPE" → "Use default RIR"; session actual-effort field "Actual RIR".
- Backward compatibility / data backfill:
  - Backfill is the conversion in `0011`. No dual-read period: this is a pilot and both clients (PWA and Capacitor iOS shell) load the web app from the deployed alias, so there is no old native binary to keep compatible.
  - Deploy order on staging: run `0011` → deploy API → deploy web. Between the API and web deploys, effort fields sent by the old web hit the legacy-`rpe` guard and are rejected (400) rather than silently lost; the window is minutes and is acceptable for the pilot. Production follows the same order after staging smoke.
