# Task: Traditional Chinese (zh-TW) localization with language switching

- Date opened: 2026-08-27
- Related contract sections: AGENTS.md §7 (sizing), §9 (task docs), §23 (Founder Constraint); `docs/frontend-ui-spec.md`
- Size (S/M/L/XL, per AGENTS.md §7): **L**

Audited source of truth: `origin/staging` @ `5afc7379148cc425ed903441528c40541202a053`.

Trigger: the first real pilot coaches are Taiwan-based and asked for a Chinese
interface. They are already using production (`https://dontworkout.vercel.app`)
today. English must be retained — the medium-term goal is reaching users
outside Taiwan, so this cannot be a one-way replacement.

**Sequencing constraint (resolved 2026-09-02):** iOS build 1.0 (4) has passed
App Store review and is live, so the hold this task was opened under no longer
applies. The architectural fact behind it still does: the Capacitor shell
loads the production web origin remotely (`server.url` →
`dontworkout.vercel.app`), so **any change shipped to production web
immediately changes what installed apps display**, with no App Store
round-trip. That now works in this task's favour — see §2 "Rollout
sequencing".

## 1. Feasibility Analysis

- Problem / trigger: The entire UI is English-only. Every user-facing string is
  a literal inline in TSX or in one of 14 per-page `errorMessage()` /
  `*AuthErrorMessage()` helpers. Taiwan pilot coaches want Traditional Chinese;
  the product still wants English for later markets.

- Options considered:
  1. **Fork an all-Chinese branch** and deploy it separately for Taiwan coaches.
  2. **Replace English strings with Chinese in place** — single language, no
     infrastructure.
  3. **Next.js official `app/[lang]/` sub-path routing** (per
     `node_modules/next/dist/docs/01-app/02-guides/internationalization.md`),
     locale in the URL, proxy-based negotiation.
  4. **Lightweight client-side locale context** — message catalogs +
     `LocaleProvider` + `useT()`, locale persisted per device, no URL change,
     no new dependency.

- Trade-offs (per option):
  1. Rejected outright. Two divergent codebases means every fix and feature is
     done twice and they drift; historically one side gets abandoned. Not
     viable for a solo maintainer.
  2. Cheapest today, but the expensive part of this task — locating every
     user-facing string across 26 files / ~6,600 lines — has to happen either
     way. Option 2 does that work and throws the English away, forcing a
     second full pass later when a non-Chinese market appears. It also
     contradicts the stated goal of keeping English.
  3. The framework-blessed approach, and correct for a public, SEO-driven,
     server-rendered site. This app is neither: **13 of 15 routes are client
     components** behind Firebase auth, so per-locale URLs buy no SEO. Costs
     are concrete and high:
     - every route moves under `app/[lang]/` (a very large diff across the
       whole `app/` tree);
     - **it breaks invite links already in circulation** — athletes have been
       given `/join/{code}` URLs; those become `/zh-TW/join/{code}` or must be
       kept working through redirects;
     - the Capacitor shell points at the bare origin, so every app launch
       gains a locale-negotiation redirect hop;
     - requires proxy/middleware this project does not currently have.
  4. Fits the actual architecture. Client pages read locale from React context;
     no routing, no URL changes, no redirect hop, no new dependency, invite
     links unaffected. Cost: the two server components (`/privacy`, `/support`)
     need separate handling (see Risks), and there are no per-locale URLs to
     share — acceptable for an auth-gated app.

- Selected option and why: **Option 4.** Per AGENTS.md §23 (Founder
  Constraint), it is the smaller implementation that reaches the real users
  who are asking for it, without the URL breakage and whole-tree churn of
  Option 3. Option 3 remains available later without rework: message catalogs
  built here are exactly what `[lang]` routing would consume if public,
  indexable, per-locale URLs ever become a requirement.

- Risks & unknowns:
  - **`/privacy` and `/support` are server components** with `Metadata`
    exports and are the only public, non-auth pages — `/privacy` is the URL
    Apple requires for account deletion. They cannot use a client locale
    context as-is. Needs an explicit decision (see §2, open decision D1); do
    not silently convert them to client components, since that drops their
    `Metadata`.
  - **14 duplicated error-message helpers** across pages
    (`app/*/page.tsx`, `components/*-sign-in-button.tsx`). Translating them
    in place preserves the duplication; consolidating them is a genuine
    cleanup but expands scope. Open decision D2.
  - `app/coach/calendar/page.tsx` is 2,195 lines and holds the densest string
    concentration; it dominates the estimate and should be its own sub-task.
  - Translation quality: strength-training vocabulary (sets/reps/RPE/load) has
    established Chinese usage among Taiwan coaches. The founder should review
    the domain terms rather than accepting machine-default translations.
  - Layout: Chinese strings are typically shorter than English but headings
    and fixed-width buttons still need a visual pass, especially the Calendar
    toolbar and the mobile Today view.
  - No locale-aware date formatting is in scope yet; `displayDate()` and
    friends hardcode `en-US` in `Intl.DateTimeFormat`. Flagged as a follow-up
    unless bundled here (open decision D3).

- Dependencies / blockers:
  - **None as of 2026-09-02.** The one blocker this task was opened with —
    App Store review on 1.0 (4) — resolved: the build passed review and is
    live, so the production locale flip is no longer held.
  - No API, schema, or backend involvement whatsoever. Frontend-only.

## 2. Technical Design

### Affected files/components

Full inventory of files carrying user-facing strings (26 `.tsx`, ~6,591 lines):

| Area | Files |
| --- | --- |
| Auth / onboarding | `app/login/page.tsx`, `app/coach/signup/page.tsx`, `app/join/page.tsx`, `app/join/[code]/page.tsx` |
| Coach | `app/coach/calendar/page.tsx` (2,195), `app/coach/calendar/{day-card,duplicate-day-panel,view-toolbar}.tsx`, `app/coach/clients/page.tsx`, `app/coach/clients/[athleteId]/page.tsx`, `app/coach/clients/invite-codes-panel.tsx`, `app/coach/workouts/page.tsx`, `app/coach/exercises/page.tsx` |
| Athlete | `app/today/page.tsx`, `app/session/[id]/page.tsx` |
| Shared | `app/settings/page.tsx`, `app/layout.tsx` (metadata), `components/{app-header,auth-hero,confirm-dialog,sign-out-button,google-sign-in-button,apple-sign-in-button}.tsx` |
| Public / server-rendered | `app/privacy/page.tsx`, `app/support/page.tsx` — **see D1** |

New files (as built in sub-task 1):

```
apps/web/lib/i18n/
  locale.ts       Locale type, detection, storage, translate(), bootstrap script
  index.tsx       LocaleProvider, useT(), useLocale()
  messages/en/{index,common,errors,settings}.ts       English — defines the key space
  messages/zh-TW/{index,common,errors,settings}.ts    Traditional Chinese
  i18n.test.ts    node:test — key parity, fallback, detection precedence
```

**One catalog file per area, not one per locale.** Sub-tasks 2–6 run as
separate sessions on separate branches (AGENTS.md §10), and every one of them
adds keys. A single `en.ts` would put all of them in conflict at the same
closing brace, and the conflict would be in the one file whose correctness
the type system depends on. Per area, each sub-task owns
`messages/en/<area>.ts` + `messages/zh-TW/<area>.ts` outright and touches one
import line in each `index.ts` — the only shared surface. Each zh-TW area
file is typed against its English counterpart (`Record<keyof typeof
enArea, string>`), so parity is enforced per area at compile time rather than
only in aggregate.

Split into `locale.ts` + `index.tsx` rather than the single `index.ts` this
plan first sketched, for one concrete reason: `node --test` strips TypeScript
types but cannot handle JSX, so anything in a `.tsx` file is untestable in
this repo — `app/coach/calendar/day-card.test.ts` and
`duplicate-day-panel.test.ts` already fail with `ERR_UNKNOWN_FILE_EXTENSION`
for exactly that reason (pre-existing, not addressed here). Keeping every
decision — precedence, fallback, storage, interpolation — in a React-free
`locale.ts` is what makes the 18 tests possible; `index.tsx` holds only the
provider and the two hooks.

### Data flow

```
app/layout.tsx (server)
  └─ <LocaleProvider>            ← client boundary, wraps existing tree
       initial locale resolution, in precedence order:
         1. localStorage "pumploop.locale"   (explicit user choice)
         2. navigator.language starts with "zh" → zh-TW
         3. fallback → en
       └─ useT() in any client component
            t("calendar.buildAndAssign") → catalog[locale][key] ?? catalog.en[key] ?? key
```

- Locale lives in React state + `localStorage`; changing it re-renders in place
  with no navigation and no reload.
- `en` is the fallback for any key missing from `zh-TW`, so a partial
  translation degrades to English rather than showing a raw key.
- `<html lang>` is corrected by a small inline `<head>` script that runs
  during HTML parsing, per Next 16's "preventing flash before hydration"
  guide. The attribute drives CJK font fallback and screen-reader voice, and
  a `useEffect` correction lands after first paint. Page *text* still paints
  once in English for a zh-TW user on a cold load: that is inherent to Option
  4 — only the server knowing the locale removes it, and reading a cookie or
  `Accept-Language` in the root layout would opt the whole app out of static
  prerendering. Accepted, and mostly hidden behind the auth-gated routes'
  existing "Loading…" state.

### Key naming

Dotted, area-first, matching the file tree so a string's home is obvious:
`login.*`, `coachSignup.*`, `calendar.*`, `today.*`, `session.*`,
`settings.*`, `clients.*`, `workouts.*`, `exercises.*`, `join.*`,
`errors.*` (shared), `common.*` (Save/Cancel/Delete/Back…).

### Frontend state/UI impact

- New language selector on `/settings` (both roles), listing 繁體中文 / English.
  Writes `localStorage` and updates context; no sign-out, no reload.
- `<html lang>` in `app/layout.tsx` must track the active locale rather than
  staying `"en"` — needed for correct font fallback and screen readers.
- No change to any route, URL, auth flow, or API call.

### Backward compatibility

- No persisted server-side state; locale is per-device only. A coach on two
  devices sets it twice — acceptable for the pilot, and cheaper than adding a
  `users.locale` column. Revisit only if coaches actually complain.
- Existing `/join/{code}` invite links keep working unchanged. This is a
  primary reason Option 3 was rejected.

### Rollout sequencing (App Review interaction)

Updated 2026-09-02: 1.0 (4) passed review and is live. The Capacitor shell
loads production web remotely, so a web deploy reaches every installed app
immediately — the property that made this risky mid-review is what makes the
rollout cheap now. Therefore:

1. Implement and merge to `staging`; verify on the staging alias.
2. Promote to production once §3 sub-task 7 verification passes. **No new
   binary, resubmission, or App Store round-trip is needed for the language
   change itself** — installed apps pick up Chinese on their next load.
3. Because the flip reaches live pilot coaches the moment production deploys,
   the manual both-locale pass in sub-task 7 is a release gate, not a nicety:
   there is no staged rollout and no per-user flag to fall back to. The
   English fallback in the catalog lookup is the only safety net, and it only
   covers missing keys, not wrong ones.
4. Separately, add zh-Hant App Store Connect localization (name, description,
   keywords, screenshots) for the Taiwan listing. That is App Store metadata,
   distinct from in-app strings, and is **not** covered by this task.

### Decisions (resolved 2026-09-02, each taking the recommendation)

- **D1 — `/privacy` and `/support`: (b) for `/support`, (a) for `/privacy`.**
  `/support` renders both languages stacked on one page; `/privacy` stays
  English-only for now. Neither page converts to a client component, so both
  keep their `Metadata` exports and `/privacy` keeps working as the URL Apple
  requires for account deletion. No server-side locale mechanism is built.
  Rationale: a legal document translated casually is worse than an English
  one, and option (c) buys a cookie-reading server path for exactly two
  pages. Revisit `/privacy` when the Chinese text is reviewed by someone who
  can stand behind it — that is a translation problem, not an engineering
  one, and it should not gate this task.
- **D2 — the 14 duplicated `errorMessage()` helpers: consolidate.** They move
  into `lib/i18n` behind one shared helper as part of sub-task 2. Every one
  of them is being touched anyway, and the duplication is the reason error
  copy has already drifted between pages; translating in place would give us
  fourteen drifting copies in two languages instead of one.
- **D4 — `fallbackWorkoutName` (OPEN — founder decision, do not implement).**
  Raised by sub-task 4, which correctly refused to decide it. When a Coach
  saves a workout without typing a name,
  `app/coach/calendar/page.tsx` generates `"Sep 3 Workout"` and **persists it**
  to the database (`page.tsx:1297`, `:1329`). Unlike every other string in
  this task it is not display copy — it is data, written once and then shown
  to the athlete, who may read a different language on a different device,
  and it never re-renders in anyone's locale.
  Options: (a) leave it English forever — consistent for everyone, wrong-feeling
  for a 繁中 coach; (b) localize it at write time — the coach gets
  `"9月3日 課表"`, but so does an English-reading athlete, permanently;
  (c) persist an empty name and render a localized fallback at display time —
  correct, and the only option that is right in both locales, but it touches
  the API contract and is therefore outside this frontend-only task.
  Recommendation: **(a) for now, (c) as a separate task.** Localizing a
  persisted, cross-user string is a worse outcome than leaving it English.
  Sub-task 6a leaves this function on `en-US` deliberately; that is the one
  intentional exception to D3.

- **D3 — locale-aware date formatting: include here.** The hardcoded
  `Intl.DateTimeFormat("en-US", …)` in `today/page.tsx` and the calendar date
  helpers becomes locale-driven, in sub-task 6. Showing a 繁中 UI with English
  weekday names is visibly half-done. This intersects the deferred
  Yesterday/Today/Tomorrow work in
  `docs/tasks/2026-08-27-today-relative-date-labels.md`: whichever lands
  second adapts to the other. Concretely — relative labels are message-catalog
  keys (`common.dateYesterday`/`Today`/`Tomorrow`), the absolute fallback is
  `Intl.DateTimeFormat(locale, …)`, and neither task should introduce a second
  date-formatting helper.
